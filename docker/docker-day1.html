🧭 1. 为什么需要 Docker

1.1 环境的痛苦

场景：项目 = FastAPI + MySQL + Redis，换一台电脑就要：

① 装 Python 3.12，配 PATH
② 装 MySQL 8.0，设 root 密码，建库
③ 装 Redis
④ pip install 几十个依赖，祈祷版本兼容

任何一步出错，项目跑不起来。"It works on my machine."

1.2 Docker 的集装箱思路

把应用程序 + 它需要的所有环境打包成一个"集装箱"。

换电脑 → 装 Docker → 拉代码 → 一行命令，全部跑起来。

不需要在新电脑上装 Python、MySQL、Redis，Docker 帮你全搞定。

1.3 Docker 用 Go 开发 + 底层三技术

技术作用通俗理解
cgroup限制进程能用的 CPU/内存"每个集装箱只能占这么多资源"
namespace隔离进程的视角（PID/NET/MNT...）"每个集装箱只看到自己的东西"
OverlayFS文件系统分层叠加"基础层 + 修改层 = 完整文件系统"

1.4 一句话记住

Docker = 把应用装进集装箱，一次打包，到处运行。

核心三词：Image（镜像）→ 只读模板 · Container（容器）→ 运行实例 · Registry（仓库）→ 存镜像

⚖️ 2. 虚拟机 vs 容器

2.1 虚拟机思路

物理机（Windows）
  └── Hypervisor（管家层）
        ├── VM1：完整 Ubuntu 系统  ← 占 4GB
        ├── VM2：完整 CentOS       ← 占 2GB
        └── VM3：完整 Windows XP   ← 占 2GB

每个虚拟机自带完整的操作系统，启动慢、占资源。
一台机器跑四五个就到头。

2.2 容器怎么省掉包袱

物理机
  └── Docker Engine
        ├── 容器1：Alpine + Redis    ← 只含应用+依赖
        ├── 容器2：Ubuntu + Python   ← 共享宿主机内核
        └── 容器3：Alpine + MySQL

没有自己独立的操作系统，没有 Hypervisor 层。
内核共用，文件系统各自独立（通过 namespace 隔离）。

2.3 数字对比

对比维度虚拟机容器
启动速度分钟级秒级
占用空间几个 GB几十 MB
一台机器能跑几个几百个
有自己内核？✅ 完整 OS❌ 共享宿主机内核
隔离级别操作系统级进程级

💡 内核 = 地基（只有一份），文件系统 = 装修（每个容器各装各的）

📦 3. 三大核心对象

对象是什么类比读写
Image（镜像）打包好的静态文件快照菜谱 / .zip 压缩包只读
Container（容器）镜像运行起来的实例按菜谱炒出来的菜可读可写
Registry（仓库）存放镜像的服务器GitHub / Docker Hub—

3.1 Image（镜像）

镜像 = 环境的完整压缩包，包含基础系统文件 + 应用 + 依赖 + 配置。静态、只读。

一个镜像可以创建无数个容器。Docker 用它直接创建容器，不需要"推断"配置。

3.2 Container（容器）

每次 docker run 镜像 → 产生一个容器。可读可写、正在运行的进程。

同一份 Redis 镜像 → docker run redis 三次 → 三个各管各的容器，数据互不影响。

3.3 Registry & Repository

Registry（注册服务器）= Docker Hub 整个网站
  └── Repository: redis      ← 某个镜像的"家"
  │     ├── Tag: latest → Image
  │     ├── Tag: 7.4    → Image
  │     └── Tag: 7.2    → Image
  ├── Repository: mysql
  │     └── Tag: 8.0    → Image
  └── Repository: nginx
DockerGitHub 类比
Registrygithub.com 整个网站
Repository某个仓库（如 Adios-8/llm-journey）
Tag版本号 / commit 标签
Image某次 commit 的完整代码快照

3.4 Dockerfile

生成镜像的配方文件。别人的镜像从 Docker Hub 拉，自己的代码靠 Dockerfile 打包成镜像。

Dockerfile（配方） → Image（菜谱） → Container（炒出来的菜）

🏗️ 4. Docker 架构

4.1 Client-Server 架构

Docker 不是一个大程序，而是两个东西在对话：

你敲 docker run redis
      ↓
Docker Client  —— 只负责收发命令
      ↓  REST API
Docker Daemon  —— 后台进程 (dockerd)，真正干活的

4.2 三个组成部分

组件角色在哪
Docker Client传话的，你敲命令的地方你的终端
Docker Daemon干活的，管理镜像/容器/网络宿主机后台
Registry存镜像的远程服务器Docker Hub

4.3 一次 docker run 全过程

① 你敲：docker run redis
② Client 通过 REST API 发给 Daemon
③ Daemon 检查本地有没有 redis 镜像
     ├── 有 → 跳到⑤
     └── 没有 → 自动去 Docker Hub 拉（不是全网搜索）
④ 分层下载镜像
⑤ 创建容器并启动

4.4 Registry vs Repository 再确认

一个 Registry 包含多个 Repository，一个 Repository 包含多个 Tag，一个 Tag 对应一个 Image。

⌨️ 5. 基本操作实战

本节所有命令已亲手敲过 ✅

5.1 docker pull — 拉镜像

docker pull redis              # 拉最新版
docker pull redis:7.4          # 指定版本
docker pull python:3.12-alpine # Alpine 精简版 (~50MB)

拉取时看到每一行 Pull complete 就是一个 Layer。

5.2 docker run — 启动容器

docker run --name my-redis -d -p 6379:6379 redis
参数含义
--name my-redis给容器起名字，方便后续管理
-d后台运行 (detach)，不占终端
-p 6379:6379端口映射：宿主机端口:容器内端口

5.3 查看容器

docker ps           # 只看正在运行的容器
docker ps -a        # 包括已停止的容器

5.4 容器生命周期

docker run 容器名      # ❌ 这是新建！不是重启
docker start my-redis   # ✅ 启动已存在的容器
docker stop my-redis    # 停止
docker restart my-redis # 重启

⚠️ 关键坑：docker run = 新建+启动，每次 run 产生新容器。重启已停止的容器用 start！

5.5 删除容器 & 镜像

# 删容器（先停后删）
docker stop my-redis
docker rm my-redis

# 删镜像（容器已删才能删镜像）
docker rmi redis:latest

# 批量清理
docker container prune    # 删所有已停止容器
docker image prune        # 删所有未使用镜像

📝 6. 编写自己的 Dockerfile

指令一览

指令作用何时执行
FROM python:3.12-alpine指定基础镜像（必须第一条）—
WORKDIR /app设工作目录，不存在则创建—
COPY . .复制文件到镜像—
RUN pip install -r requirements.txt构建时执行命令docker build 时
CMD ["python","main.py"]容器启动时的默认命令docker run 时
EXPOSE 8080声明端口（文档作用，不实际映射）—

6.1 RUN vs CMD（核心区别）

RUN  →  docker build 时执行（安装依赖、编译代码）
CMD  →  docker run 时执行（启动应用）

RUN 可以有多个，CMD 只有最后一个生效

6.2 ENTRYPOINT 配合 CMD

ENTRYPOINT = 固定的执行程序（不让用户覆盖）
CMD        = 默认参数（可以被 docker run 后面的参数覆盖）

ENTRYPOINT ["echo"]
CMD ["Default Message"]

docker run my-image           → Default Message
docker run my-image "Changed" → Changed  (只覆盖CMD，ENTRYPOINT不变)

6.3 实战：Python HelloWorld 镜像 ✅

main.py

print("Hello, Docker!")

Dockerfile

FROM python:3.12-alpine
WORKDIR /app
COPY main.py .
CMD ["python", "main.py"]
docker build -t pythontest:1.0 .
docker run --name my-python pythontest:1.0
# 输出：Hello, Docker!

6.4 缓存技巧

先 COPY 依赖文件 → RUN 装依赖 → 再 COPY 代码。改了代码但没改依赖 → 依赖层从缓存拿 → 构建快很多。

COPY requirements.txt .    # 先只复制依赖
RUN pip install -r requirements.txt  # 装依赖（改了代码这层跳过）
COPY . .                   # 再复制代码

🎼 7. Docker Compose 多容器编排

7.1 为什么需要 Compose

Docker 理念是单进程容器：一个容器只干一件事。实际项目需要多个容器协同：

✅ 容器1: FastAPI 后端     ❌ 一个容器里塞
✅ 容器2: MySQL 数据库         FastAPI+MySQL+Redis
✅ 容器3: Redis 缓存

Compose = 用一个 YAML 文件定义所有容器，一条命令全启动。

7.2 YAML 格式 & 关键配置项

配置项作用例子
image用现成镜像mysql:8.0
build从 Dockerfile 构建context: .
ports端口映射"8080:8080"
environment设环境变量MYSQL_ROOT_PASSWORD: pwd
volumes挂载数据卷（持久化）mysql_data:/var/lib/mysql
depends_on启动顺序依赖先启 mysql 再启 backend
restart: always容器挂了自动重启数据库必备

7.3 数据卷（Volumes）— 三种类型

类型写法场景
命名卷mysql_data:/var/lib/mysql数据库持久化（最常用）
宿主机卷./html:/usr/share/nginx/html开发时实时同步文件
匿名卷/app/data不推荐，删了不好找

容器的文件系统是临时的，容器删了数据就丢。卷把数据存到宿主机，跟容器生命周期分离。

7.4 Redis 持久化

方式原理特点
RDB隔一段时间拍内存快照存硬盘省资源，间隔内数据可能丢
AOF记录每次写操作到日志更安全，文件更大

7.5 实战：MySQL + Redis 双容器 ✅

docker-compose.yml

services:
  mysql:
    image: mysql:8.0
    container_name: mysql
    restart: always
    environment:
      MYSQL_ROOT_PASSWORD: password
      MYSQL_DATABASE: testdb
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql

  redis:
    image: redis:latest
    container_name: redis
    restart: always
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data

volumes:
  mysql_data:
  redis_data:
docker compose up -d      # 全启动
docker ps                  # 看到两个容器
docker compose down        # 全清理（卷保留）

7.6 代码中获取环境变量

# docker-compose.yml
environment:
  DB_HOST: mysql
  DB_PASSWORD: password

# Python 代码
import os
db_host = os.getenv("DB_HOST")  # 拿到 "mysql"

7.7 .env 安全实践

密码不写死在 yml 里 → 用 .env 文件存敏感信息 → .gitignore 忽略 → 不上传 GitHub。

# .env 文件
DB_PASSWORD=password

# docker-compose.yml 里引用
environment:
  DB_PASSWORD: ${DB_PASSWORD}

🧱 8. Docker Layer 层原理

8.1 镜像由层组成

每次 docker pull 看到的每一行就是一个层：

docker history python:3.12-alpine
# CMD ["python3"]          0B       ← 顶
# RUN apk add ...python   44.1MB    ← 装 Python 本体
# RUN apk add ...certs     2.79MB   ← 装依赖
# ENV LANG=C.UTF-8         0B       ← 环境变量
# ADD alpine-minirootfs..  9.07MB   ← Alpine 基础（底）

ENV/CMD 层大小 0B（只是元数据），RUN 装的包越大层越大。

8.2 Copy-on-Write（写入时复制）

镜像每一层是只读的。当容器要"修改"某文件时：

① 从镜像只读层找到该文件
② 复制到容器专用可写层
③ 在可写层修改

其他容器看到的还是原文件，不受影响。

💡 10 个容器共享同一份镜像文件 → 只占一份磁盘空间。改了才复制。

8.3 层复用省空间

镜像 A 和镜像 B 都基于 python:3.12-alpine → 基础层 56MB 只存一份，A 和 B 共享。

8.4 层和容器的关系

┌──────────────────┐
│  容器可写层        │  ← 每个容器独有，可读写
├──────────────────┤
│  你的代码层        │  ← 只读
├──────────────────┤
│  依赖层            │  ← 只读
├──────────────────┤
│  Alpine 基础层     │  ← 只读
└──────────────────┘

镜像 = 冻结的只读层叠
容器 = 在镜像上叠加一层自己的可写层 (Container Layer)

9 模块串联

问题：换电脑重装环境
  ↓
方案：打包成集装箱（容器）
  ↓
优势：比虚拟机轻量 100 倍（共享内核，无 Guest OS）
  ↓
核心：Image(只读文件包) → Container(运行实例) → Registry(存镜像)
  ↓
架构：Client 传话 → Daemon 干活 → Registry 供镜像
  ↓
操作：pull → run → ps → stop/start → rm → rmi → prune
  ↓
自制：Dockerfile → docker build → docker run 你自己的镜像
  ↓
多容器：docker-compose.yml → docker compose up 全启动
  ↓
原理：镜像层层叠加(只读) + 容器层(可写) + CoW 省空间
